## Contract corrections required before public API disposition

### N1 — P2: specify rejected take/cancel reentry in the normative table

**Exact contract conflict:** proposal line66 says `take/cancel` reject callback reentry before taking locks. Lines39–50 enumerate their statuses without a reentry case; line47 specifically says cancel on **any valid handle** returns0 and requests monotone refusal. Line33 specifies BUSY3 only for submit; line70 does so for shutdown. The take table otherwise permits Ready success to transfer and become Taken. There is no named status or explicit state-preservation rule for the newly rejected take/cancel calls.

**Concrete scenario:** an operation callback, or a lifetime-disposal callback, attempts to take or cancel a different live invocation H whose caller reference is valid and not being released. The early marker must refuse before its completion lock, but the table tells the callback that cancel(H) succeeds0 and refuses H, or that take(H) may consume its Ready result. Whether H remains Ready/Pending/Taken and whether later ordinary take still owns its outcome cannot be determined from the combined contract. Calling this misuse does not resolve the specified defensive rejection: unlike forged pointers or use-after-release, line66 expressly promises a runtime response to it.

**Required small correction:** add explicit higher-priority reentry rows for take and cancel, including the fixed status (BUSY3 is consistent with submit/shutdown), no completion consumption, no refusal/termination mutation, and empty valid take output. Qualify “any valid handle” with the permitted call context. Define null-argument versus reentry precedence, while preserving output clearing before every return with a valid destination. The existing release exclusion/no-op rules can stay; make clear that the lifetime callback's no-mutating-reentry obligation does not license releasing other runtime handles from that callback.

This is the remaining part of **B2**, not a request to execute future race tests during design review.

### N2 — P2: scope the new callback guard so standalone V1 behavior is not silently changed

**Exact contract/source conflict:** proposal line66 unconditionally says `init/enable/register/...` reject callback reentry; lines64/70/72 and the original brief retain existing synchronous behavior. Parent `API_CONSTRAINTS.md:14` explicitly preserves standalone V1 behavior/status provenance. In pinned `R1/mesh-rt/src/library.rs:220–236`, `mesh_library_init()` returns0 in Running; `:263–280` permits a valid callback-table registration in Running. Neither checks a callback marker. A synchronous invocation holds CALL_LOCK but releases the temporary lifecycle check before calling Mesh (`:441–478`); V1 callback selection copies the table and releases the HOST_CALLBACKS read guard before invoking the callback (`:323–341`, `:358–378`).

**Concrete scenario:** a standalone V1 embedding, with no protected/scheduled use, calls its idempotent `mesh_library_init()` helper from a native operation callback, or re-registers a valid V1 callback table there. At the pinned source these return0; registration affects subsequent calls while the in-flight callback uses its copied table. A global interpretation of line66 changes those operations to rejection without any V2 opt-in. This conclusion is source inspection, not an executed regression, and does not claim that the present app relies on either pattern.

**Required small correction:** state the activation/scope of the new reentry marker. Preserve standalone V1 init/register behavior, while refusing these mutations during V2-owned operation/lifetime callbacks before locks. If a broader V1 behavior change is intended, state it explicitly and obtain parent disposition rather than calling V1 unchanged. The new defensive nested-shutdown refusal need not preserve an old deadlock; its permitted scope/status should be stated separately. No change to legacy CALL_LOCK, wire ABI or serializer ownership is needed to resolve this.

This is a newly explicit compatibility issue introduced by the amendment's blanket guard wording; it does not reopen the original-native predicate design.

## Header, manifest and binding-consumer audit

The desktop assertion is materially correct, with one precision: `request.rs` does literal membership checks rather than constructing a declaration list or parsing C includes. `app/apps/desktop/src-tauri/src/request.rs:211–213` includes the legacy header as raw text; `:281–288` accepts a `mesh_messenger_` name when that text contains an `int32_t <name>(` line. `app/apps/desktop/src-tauri/src/mesh.rs:10` defines the three-argument Export type and `:123–140` resolves the accepted name as that type. Declaring a four-argument companion in the old header could therefore admit the wrong ABI. The proposed separate `<artifact>.invocations.h`, with no extension declarations or inclusion in the byte-identical legacy header, removes that concrete path. Support functions have a different prefix, but should stay separate as proposed.

Other inspected consumers do not force a redesign:

- `R1/meshc/src/library_bindings.rs:51–84` has one manifest row per logical export. `:118–140` and the JNI renderer consume the logical export list; `:258–275` emits JS from the original symbol/audience. Keep that list unchanged and generate companions separately. A `scheduledSymbol` field must not overwrite the legacy synchronous/borrowed-request metadata.
- `app/apps/mobile/scripts/generate-scoped-bindings.mjs:21–50` checks named fields, accepts unknown additional row fields, and pairs the generated JS with `row.symbol` and the original audience. Its175-public-operation/11-backup checks at `:52–55` remain unchanged with the same logical rows. This is a static consumer conclusion, not an executed parser or generator test.
- Mobile native routing is explicit: Swift `MeshMessengerModule.swift:301–567` and Kotlin `MeshMessengerModule.kt:399–533` select legacy MeshLibrary functions and reject unknown names. Companions are not discovered by suffix or by scanning linked symbols. Existing native serializers are visible at Swift`:298–299` and Kotlin`:395`; they remain.
- Android `CMakeLists.txt:23–27` compiles the fixed legacy JNI file with generated headers available. `MeshMessenger.podspec:19–20` collects generated headers but explicitly lists the legacy public header. Neither route adds a JS companion merely because the separate C header exists. Distinct include guards, C/C++ linkage and compiling both header include orders remain generator checks.
- `app/scripts/build-mobile-native.sh:48–62` compares h/swift/kt/jni.c/ts byte-for-byte and validates the generated ABI through the scoped-bindings consumer. Its iOS header copy at`:140–145` and Android artifact list at`:172–174` do **not** package the new invocation header. That is a future opt-in packaging task, not a current legacy break or permission to broaden this review's edit scope.
- The retained qualification consumer `app/ops/attachment-paid-native/build.py:45–61` compares full ABI JSON except target. Added companion metadata will invalidate old expected-ABI receipts; fresh receipts must be generated from the new exact artifacts. This is intended qualification drift detection, not evidence that row-additive metadata is intrinsically incompatible. There is no checked-in app-generated ABI JSON at the probed `generated/libmessenger_mobile.abi.json` path; this review makes no candidate manifest-content claim.
- Desktop adoption must satisfy the new code/context lifetime contract: `mesh.rs:33–36,164–175` currently owns a Library and Box<Host> and shuts down before those fields drop. That existing V1 wrapper cannot simply start scheduled work and continue treating shutdown as permission to drop them. Explicit V2 code pinning and retained context are adoption gates already implied by lines60–62; the standalone V1 wrapper is not approved for V2 use by this review.

No additional blocking consumer was found in these inspected routes. Actual compiler output equality, symbol inventories, platform linking and packaging remain unexecuted. There is no claim of all-platform compatibility from a source scan.
