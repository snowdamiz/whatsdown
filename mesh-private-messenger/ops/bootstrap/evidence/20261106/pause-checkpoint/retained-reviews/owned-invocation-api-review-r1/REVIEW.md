## B1 — P1: define last-reference disposal and shutdown quiescence

**Contract anchors:** proposal lines 15, 17, 22 and 34. It promises nonjoining release, retained original Host ownership, callbacks on the scheduler worker's native stack, and valid handles after runtime stop. It does not specify the executor and blocking/reentrancy contract of the V2 lifetime `release` callback, or whether shutdown settles detached HTTP workers.

**Concrete source boundary:** `authority.rs:47–57` calls the native lifetime callback synchronously in `NativeAuthority::drop`; the final `Arc` determines its thread. The normal-stack trampoline at `library.rs:358–378` / `actor/stack.rs:119–139` covers the nine operation callbacks, not this lifetime callback. `library.rs:242–258` holds CALL_LOCK and LIFECYCLE while joining scheduler workers. HTTP uses an unretained thread join handle at `http/client.rs:848–867`; `scheduler.rs:418–422` joins scheduler workers only.

**Failure scenario requiring a contract decision:** native releases its authority reference after submit; the process finishes and its invocation handle becomes the last retained context. `invocation_release` can then synchronously call Host release on the caller's thread, potentially after shutdown. If instead the HTTP worker is last, it can invoke that callback on its HTTP thread. A scheduler-only shutdown can finish while a cancelled root's accepted HTTP still owns runtime/Host code. Neither “nonjoining refdrop” nor “runtime stop” tells an adapter when it may dispose of executor-bound Host state or unload that code. Running an arbitrary lifetime callback under the completion/lifecycle lock can also turn a short API operation into a deadlock. This is an unspecified embedding obligation, not a claim that the proposed implementation already contains that bug.

**Required correction:** distinguish operation callbacks from lifetime callbacks and make the following explicit before freezing the API:

- Name which executors may make the final lifetime release, including caller release after shutdown and detached-worker exit. Require the lifetime callback to be safe there, bounded/nonjoining, and unable to wait for or reenter the runtime; alternatively specify owned deferred disposal on an executor that remains available. JSI objects remain outside these owners.
- Never invoke Host release, process destructors, Mesh termination code, or foreign cleanup while holding lifecycle/completion/process-table locks. Detach ownership under the lock and dispose outside it. Reentrant submit/invoke/shutdown refusal must occur before taking locks or joining the current worker. Existing synchronous V1 behavior must remain separately accounted for.
- State exactly what shutdown joins. Either define a V2 worker-quiescence fence, or explicitly make shutdown scheduler-only and provide a usable rule/mechanism for retaining and eventually releasing runtime/Host code while HTTP workers remain. Do not silently promise that scheduler shutdown permits unloading, and do not silently change V1's blocking contract. After shutdown, outstanding handles must still have terminal outcomes and usable take/release/free operations; the code backing those operations stays loaded until their ownership ends.

A prose decision is required now; barrier tests for last-release and shutdown are required later. No new publication capability follows from either choice.

## B2 — P2: complete the observable C state/status contract

**Contract anchors:** proposal lines 7 and 10–15 introduce functions returning `int32_t`; lines 11, 22 and 34 describe once-only take and cancellation ordering. They leave `cancel`'s returned status unspecified, do not say whether cancellation before root cleanup leaves take PENDING, and omit the all-path output/null-handle rules and terminal error consumption rules. “Cancel-first discards pending result/refuses” must not permit a terminal take before the root cleanup promised on line 22.

**Concrete source boundary:** `authority.rs:292–295` clears scoped output before validation. `library.rs:430–435` defines limit rejection; `library.rs:481–498` defines protected refusal/application-error/panic precedence. `library.rs:536–565` copies into independently allocated bounded output, and `library.rs:573–589` frees/wipes using private allocation length. These observable choices cannot be inferred solely from “existing statuses” for the new asynchronous functions.

**Required correction:** add a small normative transition/status table. A coherent choice, which the owner may explicitly adopt or replace, is:

- Valid submit output is set to null before any failure; status 0 transfers one caller reference only after owned admission/enqueue succeeds. Nonzero status leaves no caller handle or executable orphan. Null authority/output, null input with nonzero length, invalid limits, unavailable runtime, nested entry, and oversize input have named fixed statuses. Preserve exact per-export limits, 1 MiB defaults / 64 MiB ceiling, and callback limits independently.
- A valid take output is reset to `{NULL,0}` before every return. Require an empty destination, or explicitly define who frees an earlier returned allocation. Invalid output must not consume the result. PENDING=12 and TAKEN=13 return no bytes. A terminal result, including fixed errors/refusal, is consumed once; all subsequent valid takes are 13. Only success can carry private output; protected application/panic/error paths carry no raw payload. Name allocation-failure behavior and preserve the existing allocator/free pairing after handle release and runtime shutdown.
- Cancellation is a monotone invocation flag distinct from completion. Cancel while Pending schedules safe-point termination but leaves take at 12 until root unwind/resource cleanup finishes, then yields one terminal refusal10. Cancel before a Ready result is taken wipes/replaces that result with refusal10. Cancel after Taken must not recreate a result; it can still refuse/stop surviving descendants. Specify idempotent return values for all three states (for example 0 for every valid handle, 1 for null).
- Set refusal and select the cancel-versus-take winner in the same defined critical section. Two simultaneous takes have one terminal winner. Independent generation retirement follows the original monotone scan rule at take: retirement-first refuses/wipes; transfer-first may return only the already selected native bytes. Cancellation/retirement after transfer cannot recall those bytes or authorize publication.
- Concurrent take/cancel are allowed on a live borrowed handle; release consumes the sole caller reference and must be externally excluded from all such uses. Pointer copies do not create references. Define null release as a no-op; double release/use-after-release is outside the valid ABI. Internal owners independently retain execution state.
- Define “nonblocking take”: for example, it never waits for root execution, I/O or an executor, but permits brief completion-lock serialization and is not a lock-free guarantee. If lock contention instead returns a status, name that status without confusing contention with root completion.

These are API semantics, not a demand to execute the eventual race suite during design review.

## Companion symbols and compatibility: viable with an explicit inventory

The clarification on proposal line 32 resolves the earlier “exactly 176 physical symbols” concern. Keep exactly the existing logical rows/legacy entrypoints, limits, wire formats, audiences and JS routes; add the native companions to a separate physical-symbol inventory. A second descriptor-routing abstraction is not required merely to avoid acknowledging the additional symbols.

There is direct source support for this shape. `library_bindings.rs:71–84` builds one manifest row per logical export; `library_bindings.rs:258–275` generates JS from the existing logical symbol and audience. The frozen app consumer `generate-scoped-bindings.mjs:21–50` accepts unknown row fields, selects `row.symbol`, and checks the existing audience; `:54` checks 175 JS-visible operations. Adding only `scheduledSymbol` to those same rows does not, by inspection of this consumer, create another JS operation. This is a source conclusion, not a claim that every consumer or regenerated artifact was tested.

Before companion publication, inventory legacy symbols, companions and runtime support symbols together; reject collisions such as an existing `x_submit_v2` export colliding with the companion of `x`. `mesh-codegen/src/codegen/mod.rs:421–435` currently checks the legacy wrapper name and emits a private pointer-based entry thunk. Reuse that ABI-safe thunk shape (`library.rs:49–50`), not a raw aggregate-return lowered function masquerading as the actor entry ABI. Resolve names deterministically without renaming an existing legacy operation.

The sidecar must distinguish scheduled native invocation semantics from the legacy top-level `ownership.request = borrowed-for-call` and `nativeAuthorityExtension.scheduling = synchronous` at `library_bindings.rs:51–69`. Keep legacy metadata true; attach copied-input/owned-handle/native-only/capability4 semantics to the companion metadata. An existing logical audience of “all” does not make its new companion a JS-selectable operation. The runtime bounded-submit helper remains compiler/native infrastructure; request bytes must never select its function pointer or limits. Verify generated Swift/Kotlin/JNI and all actual app consumers as compatibility gates.
