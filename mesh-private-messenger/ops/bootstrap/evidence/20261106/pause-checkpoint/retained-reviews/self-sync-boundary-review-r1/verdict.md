**Blocking finding R1 (high): a packet-controlled account key can satisfy the same-account admission predicate.**

The new releases are at proposed [messages.mpl:339](inputs/proposal/messages.mpl#L339) and [messages.mpl:357](inputs/proposal/messages.mpl#L357), reached from initial receive at [messages.mpl:581](inputs/proposal/messages.mpl#L581). The evidence chain is:

1. Initial receive decodes `initiator_account` from `packet_account_identity` at [messages.mpl:405](inputs/proposal/messages.mpl#L405) and passes it to `receive_initial_at_minimum_suite` at line 472. The local account passed separately at line 467 verifies the responder side; it does not replace the initiator trust root.
2. The handshake verifies the initiator credential against that supplied account at [session/handshake.mpl:567](inputs/live-source/mesh-private-messenger/packages/messenger-protocol/session/handshake.mpl#L567). Credential verification checks equal account IDs and verifies the signature using `account.authorization_public_key` at [identity/device.mpl:293](inputs/live-source/mesh-private-messenger/packages/messenger-protocol/identity/device.mpl#L293).
3. Account ID is not a self-authenticating key hash: generation chooses the ID independently of the signing key at [identity/device.mpl:96](inputs/live-source/mesh-private-messenger/packages/messenger-protocol/identity/device.mpl#L96). The identity codec checks lengths/version/extensions, not an ID-to-key binding, at [protocol/identity_wire.mpl:26](inputs/live-source/mesh-private-messenger/packages/messenger-protocol/protocol/identity_wire.mpl#L26).
4. `self_sync` checks type 2 and `peer.account_id == local.account_id` at [messages.mpl:508](inputs/proposal/messages.mpl#L508). The mismatch predicate at line 531 checks the peer identity against the packet identity, the inner sender account/device against the peer, the device ID against the initiator credential, the recipient device, and the conversation. It never compares the initiator authorization key with the locally trusted account key. Profile decoding at [transport/packet.mpl:306](inputs/live-source/mesh-private-messenger/packages/messenger-protocol/transport/packet.mpl#L306) establishes internal ID consistency, not this missing trust relation.

Concrete source counterexample: take a normal unblocked receiver with an available prekey and no conflicting self-session; copy its account ID into a newly constructed account identity carrying an attacker-controlled authorization key. Sign an attacker device credential under that key. Supply a consistent peer profile and valid handshake ciphertext whose type-2 inner envelope names that account ID, that device, the actual recipient device, and the deterministic self-sync conversation. The sender can calculate that conversation from the account ID using [sessions.mpl:579](inputs/live-source/mesh-private-messenger/packages/mobile-core/mobile/sessions.mpl#L579). No victim account signing key is required by the traced checks. Recipient sealing establishes delivery to the receiver, not sibling authorization.

The remaining pre-release gates do not repair the binding: `require_log_changes_allowed` checks retained fork/slashing state ([transparency_safety.mpl:31](inputs/live-source/mesh-private-messenger/packages/mobile-core/mobile/transparency_safety.mpl#L31)); absent fanout reservations are allowed ([fanout_prekeys.mpl:220](inputs/live-source/mesh-private-messenger/packages/mobile-core/mobile/fanout_prekeys.mpl#L220)); gossip with no applicable extension can return normally ([gossip.mpl:393](inputs/live-source/mesh-private-messenger/packages/mobile-core/mobile/gossip.mpl#L393)); session sealing records the supplied peer. A changed safety number clears verification/sets `key_changed`, rather than refusing the sender ([sessions.mpl:762](inputs/live-source/mesh-private-messenger/packages/mobile-core/mobile/sessions.mpl#L762)).

Such an input reaches the proposed status classification and, for a valid payload targeting a different account, the five-field release. The downstream route can create an alias, append outgoing history, and prepare request-acceptance writes for that target ([messages.mpl:582](inputs/proposal/messages.mpl#L582), [history.mpl:456](inputs/live-source/mesh-private-messenger/packages/mobile-core/mobile/history.mpl#L456)). These are source-derived consequences, not a reproduced exploit or evidence of production exploitation. The missing binding predates this patch, but the new reasons explicitly depend on authenticated sibling authority, so it blocks approving these releases.

The ratchet caller is private-helper-safe only if its session provenance is safe. Actual public `receive_message` loads/restores a session and reaches the helper only after `decrypt -> Opened`, type/account/device/recipient/conversation checks, and blocked/control/invitation exclusions ([messages.mpl:856](inputs/proposal/messages.mpl#L856), [messages.mpl:907](inputs/proposal/messages.mpl#L907), [messages.mpl:918](inputs/proposal/messages.mpl#L918), [messages.mpl:972](inputs/proposal/messages.mpl#L972)). However, a session admitted by the initial route above can retain the claimed local account ID and the attacker's device ID. Ratchet authentication proves possession of that session's keys; it does not retrospectively establish sibling authorization. The record has IDs, safety metadata and a transport key, without a directly stored account authorization key ([types.mpl:123](inputs/live-source/mesh-private-messenger/packages/mobile-core/mobile/types.mpl#L123)).

Required correction: establish the sender credential's binding to the locally trusted account authority, including the applicable device-authorization policy, before allowing self-sync releases or accepting its session as a sibling session. Supply an explicit provenance/revalidation disposition for existing and restored same-account sessions; fixing only future initial receives is insufficient evidence for the ratchet release. Re-run the exact initial and ratchet counterexamples below after the owner composes the change. This review does not prescribe a new public authorization helper or authorize source edits.

**The parser and release shape are reasonable, conditional on repairing R1 and proving composition.**

The pure typed parser has exactly three nullary errors at [sessions.mpl:69](inputs/live-source/mesh-private-messenger/packages/mobile-core/mobile/sessions.mpl#L69), with no declassification in the parser or legacy wrapper. `parse_sync_payload` maps them to the legacy fixed strings; it does not release an arbitrary error string. Source comparison against the frozen CLI-base Sessions file preserves the parsing order and the following distinctions:

| Condition | Result/status | Precedence |
| --- | --- | --- |
| Reader/main-vector failure, trailing bytes, invalid username or required field length/value | `invalid_sync_payload` / 1 | Main vectors precede the optional tail; final field validation follows the tail and end check. |
| Present optional safety tail with broken framing, truncation or vector length above 64 | `invalid_store_request` / 2 | Occurs before the final end/semantic checks. |
| Successfully framed safety value with length 1–63 | `invalid_safety_number` / 3 | Occurs before the final end/semantic checks. |
| Missing safety tail, or a framed empty/64-byte value | Parsing may succeed | Later failures still apply. |
| Fully parsed payload targeting the local account | `invalid_sync_payload` / 1 | Own-target comparison happens only after parsing succeeds. |
| Valid payload targeting another account | 0 | Only this arm projects metadata. |
| Any other published status | Fixed `invalid_sync_payload` | No metadata projection. |

Relevant implementations are [sessions.mpl:97](inputs/live-source/mesh-private-messenger/packages/mobile-core/mobile/sessions.mpl#L97), [sessions.mpl:229](inputs/live-source/mesh-private-messenger/packages/mobile-core/mobile/sessions.mpl#L229), and [messages.mpl:322](inputs/proposal/messages.mpl#L322). For example, an own-target payload with a malformed optional tail must retain the tail error; own-target rejection must not mask it. The finite release is exactly four status outcomes, not a `Result` or arbitrary diagnostic. It still discloses a private classification, so its finiteness alone supplies no authority.

The second site explicitly projects five fields. Their existing uses are visible in [sessions.mpl:634](inputs/live-source/mesh-private-messenger/packages/mobile-core/mobile/sessions.mpl#L634), [header_admission.mpl:173](inputs/live-source/mesh-private-messenger/packages/mobile-core/mobile/header_admission.mpl#L173), and [sessions.mpl:151](inputs/live-source/mesh-private-messenger/packages/mobile-core/mobile/sessions.mpl#L151):

| Field | Existing purpose and limit |
| --- | --- |
| `peer_account_id` | Exact 32 bytes; peer lookup, alias label, source capture and request acceptance. It is not the authenticated sibling sender ID. |
| `conversation_id` | Exact 16 bytes; missing-peer alias/history route. An existing peer's stored conversation wins. After VO composition it also supplies the original sync conversation for attachment binding. |
| `peer_username` | Nonempty UTF-8 in a vector capped at 64 bytes; copied to a new alias's session metadata. It is sibling-supplied text, not independent directory verification. |
| `disappearing_seconds` | Parsed four-byte value; alias policy and reconstructed history expiry metadata. No body-content release is needed. |
| `safety_number` | Empty or 64 bytes; copied to a new alias, whose `verified` flag remains false. Length validation is not proof of the target's identity or safety number. |

Application policy may deliberately treat these as public routing/display metadata supplied by a genuinely authorized sibling; it need not pretend they were independently verified as the target peer's cryptographic identity. That is an explicit metadata-release policy, not an automatic consequence of parsing or ciphertext authentication. The tuple is bounded but is not a finite classification like the status: username and safety bytes can carry sender-chosen content. The parent must accept that exact metadata class as releasable after admission. All five are released on every status-0 path even though an existing alias does not consume every field; this is the union of the current callers' needs, not branch-minimal release.

`body`, embedded `client_message_id`, and embedded `client_timestamp` are absent from the tuple and retained from the private parse. The fallback timestamp comes from the enclosing `InnerEnvelope`; the fallback is source-inert on status 0 because the same exhaustive status function maps every parse error to 1/2/3. `attachment_manifest` is not projected and remains on its existing separate argument path. These are source-shape observations; compiler preservation of payload and caller-PC taint is an outstanding gate.
