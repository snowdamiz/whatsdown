**D1 — High: define busy-handler recovery for every prepare outcome, including an error after the setting changed.**

The proposed sequence is “execute canonical timeout configuration … record … then install the runtime busy handler” ([proposal, line 34](/Users/andreyyurlov/Documents/dev/mesh-lang/.tmp/native-owned-invocations/core-sqlite-prerequisite/PROPOSAL.md:34)). That must not mean replacement only after successful preparation.

Counterexample: canonical prepare executes `sqlite3_busy_timeout(db, 1000)`, replacing any existing custom handler. A subsequent allocation in preparation fails. SQLite reports an error and finalizes the partial VM, but does not undo the handler change. If Rust returns early through `?`, the connection still owns SQLite's stock timeout handler. A caller that handles the SQL error and reuses the connection now gets waits without the original-context/resource checks or aggregate deadline. Core's immediate close on this error is helpful but cannot establish the runtime contract for every caller.

Evidence: [SQLite, lines 145189–145195](/Users/andreyyurlov/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/libsqlite3-sys-0.36.0/sqlite3/sqlite3.c:145189) performs the setter before returning a statement; [lines 186685–186699](/Users/andreyyurlov/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/libsqlite3-sys-0.36.0/sqlite3/sqlite3.c:186685) replaces the handler; [lines 146430–146465](/Users/andreyyurlov/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/libsqlite3-sys-0.36.0/sqlite3/sqlite3.c:146430) can turn post-parser allocation failure into an error. The stock callback counts waits per locking event and has no authority checks ([lines 186560–186599](/Users/andreyyurlov/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/libsqlite3-sys-0.36.0/sqlite3/sqlite3.c:186560)). This is a source-derived failure schedule, not an executed fault-injection result.

Minimal amendment: create the cleanup obligation before invoking canonical prepare. On every return, while still inside admitted `SqlPrepare::execute` and holding the connection, leave either the valid runtime handler or a disabled/no-wait handler. Specify whether a failed setting keeps the prior safe timeout policy or invalidates/closes the connection. Never leave a stock-handler interval available to a later operation. Outside an active admitted operation, the callback must return 0. Pin the callback's storage through statement finalization, rollback and connection close, or unregister it before its storage dies. This also covers Rust unwind outside C; it does not justify unwinding through a C callback. Secure-delete settings are not transactionally undone by prepare errors: never “restore” privacy by turning secure deletion off.

Required evidence: force failure after the timeout setter but before prepare returns; retain/reuse the connection and prove the next contention cannot use the stock handler, stale deadline or expired context pointer. Include initial configuration and repeated configuration on an already-configured connection.

**D2 — Medium: restore a stable policy cell, not the authorizer registration; define nested/reprepare behavior.**

The proposal correctly requires a temporary per-connection policy confined to admitted preparation ([line 24](/Users/andreyyurlov/Documents/dev/mesh-lang/.tmp/native-owned-invocations/core-sqlite-prerequisite/PROPOSAL.md:24)), but it must rule out the straightforward implementation that installs an allowing authorizer and calls `sqlite3_set_authorizer` again to restore the denying authorizer.

Counterexample: canonical prepare succeeds and changes the setting; restoring the ordinary callback through `sqlite3_set_authorizer` expires the statement. The separately admitted `sqlite3_step` then reparses it under ordinary PRAGMA denial. Core receives failure despite the setting having changed. Extending the allow policy through step to fix that would violate the stated prepare-only boundary and could reapply `busy_timeout`, replacing the runtime handler again.

Evidence: [SQLite, lines 124138–124151](/Users/andreyyurlov/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/libsqlite3-sys-0.36.0/sqlite3/sqlite3.c:124138) expires prepared statements even when registering a non-null authorizer with the same function; [lines 93158–93172](/Users/andreyyurlov/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/libsqlite3-sys-0.36.0/sqlite3/sqlite3.c:93158) and [93304–93309](/Users/andreyyurlov/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/libsqlite3-sys-0.36.0/sqlite3/sqlite3.c:93304) connect expiration to automatic reprepare.

Minimal amendment: install one authorizer with stable connection-owned callback state. RAII changes/restores only that state inside admitted prepare. The callback must not reacquire the already-held connection mutex. Specify exact prior-state restoration or fail-closed rejection of nested configuration; do not let an inner guard accidentally clear or extend an outer privilege. A policy must never escape into ready-step. Unexpected reprepare of a configuration statement must fail closed under ordinary policy, with an explicit result; no automatic allowance/retry that reapplies the setter. Ordinary statements retain ordinary authorization during SQLite's internal reprepares.

Required evidence: both canonical statements prepare and separately step successfully with ordinary policy restored; a following prohibited PRAGMA is refused. Exercise prepare failure, outer Rust unwind, attempted nesting, and forced expiration/reprepare. Assert configuration is not silently reapplied and the custom busy handler survives.

**R1 ownership, admission and local settlement otherwise fit the design.**

The connection registry retains an `Arc<Mutex<SqliteConn>>`, and ownership is exact `Arc::ptr_eq`, not generation equality or a current-owner lookup ([sqlite.rs, lines 66–142](/Users/andreyyurlov/Documents/dev/mesh-lang/.tmp/native-owned-invocations/audit-r1/snapshot/compiler/mesh-rt/src/db/sqlite.rs:66)). `run_statement` holds that retained connection and its lock across prepare and ready-step ([lines 426–476](/Users/andreyyurlov/Documents/dev/mesh-lang/.tmp/native-owned-invocations/audit-r1/snapshot/compiler/mesh-rt/src/db/sqlite.rs:426)). The setting enum can therefore select fixed runtime SQL without introducing a new permit or callback transaction.

`perform` registers local settlement before its liveness scan, consumes one exact effect, and decrements only after execution ([authority.rs, lines 243–272](/Users/andreyyurlov/Documents/dev/mesh-lang/.tmp/native-owned-invocations/review-input-r2/source/compiler/mesh-rt/src/authority.rs:243)). The frozen R1 snapshot has the same relevant ordering ([R1 authority, lines 191–220](/Users/andreyyurlov/Documents/dev/mesh-lang/.tmp/native-owned-invocations/audit-r1/snapshot/compiler/mesh-rt/src/authority.rs:191)); its SQLite file is byte-identical to the proposal-pinned SQLite source. Install policy and callback/deadline guards inside the effect, not before admission or after settlement. Keep ready-step separate. Validation may precede admission; mutation must not.

Retirement before prepare admission must leave the settings unchanged. Retirement after admitted prepare can leave its setting applied; it must refuse ready-step and later effects. This is already the correct distinction in proposal line 26. Return success cannot grant future work or publication. Handle removal prevents later lookup but an active statement retains its connection ([sqlite.rs, lines 697–709](/Users/andreyyurlov/Documents/dev/mesh-lang/.tmp/native-owned-invocations/audit-r1/snapshot/compiler/mesh-rt/src/db/sqlite.rs:697)); a new callback pointer must retain the same protection, without forming an ownership cycle or pointing at a dropped operation frame.

**Resource accounting is not inherently self-defeating; transaction and cancellation checks need precise rules.**

`local_inflight` and `InvocationContext.resources` are different counters. `perform` increments the former; `resource_scope` increments the latter ([authority.rs, lines 152–180](/Users/andreyyurlov/Documents/dev/mesh-lang/.tmp/native-owned-invocations/review-input-r2/source/compiler/mesh-rt/src/authority.rs:152), [253–257](/Users/andreyyurlov/Documents/dev/mesh-lang/.tmp/native-owned-invocations/review-input-r2/source/compiler/mesh-rt/src/authority.rs:253)). Current SQLite execution does not install a `ResourceScope`. Thus a lone accepted SQL operation can have local settlement outstanding and still have zero *other* resources. Do not test `local_inflight == 0`, or blindly subtract one from `resources`. If implementation adds an own-resource guard, distinguish it structurally. The connection mutex and SQLite's internal locks necessarily remain held; “other resource” cannot mean those locks too.

Capture the same retained original context for busy checks. Do not call `suspend_or_stop`: it unwinds, and `yield_current` invokes it ([stack.rs, lines 99–113](/Users/andreyyurlov/Documents/dev/mesh-lang/.tmp/native-owned-invocations/review-input-r2/source/compiler/mesh-rt/src/actor/stack.rs:99)). No callback may reacquire runtime locks, call SQLite, enter Host/Mesh, close/finalize, park, schedule disposal or unwind. It must also avoid becoming the last owner whose drop invokes a foreign release callback inside C.

The transaction cache is synchronized from `sqlite3_get_autocommit`, not SQL text ([sqlite.rs, lines 73–95](/Users/andreyyurlov/Documents/dev/mesh-lang/.tmp/native-owned-invocations/audit-r1/snapshot/compiler/mesh-rt/src/db/sqlite.rs:73)). Sample actual autocommit under the retained mutex before entering C; check the original context's transaction/resource counts as well, including another connection's transaction. Never call SQLite from the busy callback to discover this. Test raw BEGIN/COMMIT/ROLLBACK, outer and nested SAVEPOINT/RELEASE, failed upgrade/commit and automatic rollback, rather than only wrapper methods. An implicit transaction inside the already-admitted statement is distinct from a transaction held across Mesh calls. Cleanup with no active effect budget must not wait or acquire new authority.

Check liveness immediately before sleep and again after sleep before returning nonzero. The guarantee is not atomic cancellation of SQLite: retirement can occur after the last successful scan and before SQLite's retry/write. An already-admitted operation may finish under R1. A callback observing retirement must return 0; a controlled retirement *during a sleep slice* must prevent the post-sleep retry. Do not broaden that test into “no write after cancellation returns.” Keep local settlement until C returns and operation-owned cleanup ends. Cancellation is monotone refusal and safe-point stopping ([invocation.rs, lines 59–71](/Users/andreyyurlov/Documents/dev/mesh-lang/.tmp/native-owned-invocations/review-input-r2/source/compiler/mesh-rt/src/library/invocation.rs:59)); the scheduler marks processes, then unwinds on its owner worker ([scheduler.rs, lines 315–328](/Users/andreyyurlov/Documents/dev/mesh-lang/.tmp/native-owned-invocations/review-input-r2/source/compiler/mesh-rt/src/actor/scheduler.rs:315), [984–1039](/Users/andreyyurlov/Documents/dev/mesh-lang/.tmp/native-owned-invocations/review-input-r2/source/compiler/mesh-rt/src/actor/scheduler.rs:984)). Do not close the connection from the cancelling thread. Root cleanup closes SQLite before publishing Ready ([1162–1165](/Users/andreyyurlov/Documents/dev/mesh-lang/.tmp/native-owned-invocations/review-input-r2/source/compiler/mesh-rt/src/actor/scheduler.rs:1162), [1231–1235](/Users/andreyyurlov/Documents/dev/mesh-lang/.tmp/native-owned-invocations/review-input-r2/source/compiler/mesh-rt/src/actor/scheduler.rs:1231)); this review does not certify R2's broader Ready implementation.

**The 1000 ms budget must name the admitted unit and its limits.**

Use one deadline per admitted `SqlPrepare` and one per admitted `SqlStatement`, starting inside execution. `SqlStatement` query execution contains a loop of `sqlite3_step` calls ([sqlite.rs, lines 407–423](/Users/andreyyurlov/Documents/dev/mesh-lang/.tmp/native-owned-invocations/audit-r1/snapshot/compiler/mesh-rt/src/db/sqlite.rs:407), [479–507](/Users/andreyyurlov/Documents/dev/mesh-lang/.tmp/native-owned-invocations/audit-r1/snapshot/compiler/mesh-rt/src/db/sqlite.rs:479)). Resetting on every row, busy count of zero, locking event, or internal reprepare loses the aggregate bound. Preparation and ready-step remain two admissions, so this design does not promise 1000 ms for the whole public execute call.

SQLite may return BUSY without invoking its handler to avoid deadlock ([SQLite, lines 3310–3324](/Users/andreyyurlov/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/libsqlite3-sys-0.36.0/sqlite3/sqlite3.c:3310)); lock release within budget does not guarantee success in every lock topology. Do not retry whole statements or transactions automatically. Native sleep blocks the sole scheduler lane: another invocation progresses after this finite operation exits, not while the callback sleeps. A lock holder that itself needs that lane cannot release it during the wait; expiry/no-wait must recover progress. No hard bound covers scheduler preemption, filesystem stalls or SQLite work that never calls the busy handler. Keep ordinary VM limits.

**Grammar, mode and status gates must precede every setting.**

Complete byte-string recognition plus bounded ASCII-only trimming and runtime-owned canonical SQL is sufficient in principle. Reject both recognized setters on every query entry point before preparing; validate empty parameters and V2 quota before setting. Legacy preparation currently precedes parameter decoding/binding ([sqlite.rs, lines 325–352](/Users/andreyyurlov/Documents/dev/mesh-lang/.tmp/native-owned-invocations/audit-r1/snapshot/compiler/mesh-rt/src/db/sqlite.rs:325)), so routing the enum through that unchanged ordering is unsafe. Cover text, typed and typed-V2 execute/query variants ([lines 721–790](/Users/andreyyurlov/Documents/dev/mesh-lang/.tmp/native-owned-invocations/audit-r1/snapshot/compiler/mesh-rt/src/db/sqlite.rs:721)).

Exact comparison must consume the complete Mesh string, including embedded NULs, before choosing canonical SQL. Reject semicolons, comments, suffix/second statements, altered case/spacing beyond the allowed outer trim, qualifiers, quoting, numeric alternatives and parameters. Never grant policy from a prefix and later rely on SQLite's tail pointer: current preparation discards tails ([sqlite.rs, lines 246–255](/Users/andreyyurlov/Documents/dev/mesh-lang/.tmp/native-owned-invocations/audit-r1/snapshot/compiler/mesh-rt/src/db/sqlite.rs:246)). Ordinary SQL with an ignored tail is existing behavior; the proposal must not claim that it newly rejects *all* ordinary SQL tails. The essential invariant is no partially accepted setter. The authorizer must check exact name/value, null unqualified database and canonical origin; all other rules remain denied as today.

Do not invent a PRAGMA readback or rows-changed result. Existing execute returns `sqlite3_changes` even for a statement yielding a row; Core ignores that payload. Installing a custom busy handler resets SQLite's `busyTimeout` to zero ([SQLite, lines 186628–186643](/Users/andreyyurlov/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/libsqlite3-sys-0.36.0/sqlite3/sqlite3.c:186628)). The proposed execute-only compatibility can acknowledge that difference while continuing to deny query/readback. Preserve sticky authority refusal for policy violations and distinguish it from live-authority contention/application errors. No private SQLite error payload should escape protected native completion; no new public ABI statuses are needed.
