The proposed order is: framing → loader/pruning → current time → pure preparation → conditional renewal view → pure completion → invitation encoding → context construction → final seal → original caller commit. There is no speculative storage operation. Preparation failure makes renewal false and bypasses the view; the same failure then propagates through `encoded` without encoding. Renewal-view failure returns immediately before completion/encoding. The final `Result.unwrap_or(encoded, Bytes.empty())` is executed only after the success gate on that identical immutable result; its empty fallback cannot reach sealing on an error. No fallback is sealed before a pending `?`. The unreachable `Ok` arm in error extraction likewise does not replace any reachable original error. These are source-level arguments to validate against the compiler, not runtime evidence.
