# Compatibility Matrix

| Feature | Wire/version identifier | Persistence | Compatibility rule | Production status |
|---|---|---|---|---|
| Classical one-to-one | protocol `1`, suite `0x0001` | ratchet snapshot `3`; `2` is read and rewritten as `3`; `1` is read, without its skipped keys, and rewritten as `3` | Authenticate the selected suite; reject unknown mandatory extensions and downgrade below the strongest observed suite; no new session below the config's minimum suite | Reachable; exact-candidate internal verification required |
| Hybrid one-to-one | protocol `1`, suite `0x0002` | ratchet snapshot `3`; `2` is read and rewritten as `3`; `1` is read, without its skipped keys, and rewritten as `3` | Explicit negotiation only; classical fallback is permitted only when the authenticated peer does not advertise hybrid support and the config's minimum suite is `1` | Reachable experimental construction; internal verification required |
| Encrypted headers and post-quantum ratchet | ratchet message `4` ([`ratchet-message-v2.md`](ratchet-message-v2.md)); inner-envelope extension `3` (session features: `1` message 4, `2` post-quantum ratchet, `4` session reset, `8` deniable group messages) | ratchet snapshot `3` (header keys under purpose `4`, earlier header keys and the ratchet's seed and secret in `SecretMap`s under purpose `12`) | A session moves to message `4` at the sender's next sending root step after the peer advertised it, in an authenticated message; receivers read message `4` without recording anything; never back to a cleartext header for a new chain; the post-quantum ratchet only in suite `0x0002` sessions; message `4` only inside `RCP` | Reachable between current clients; builds older than this one cannot read message `4` or snapshot `3` |
| Session reset | inner message types `5` (`SRQ` `1` request, in the broken session) and `6` (`SRA` `1` answer, first message of the new session) ([`session-reset-v1.md`](session-reset-v1.md)) | session record adds reset state, reset time and the peer's identity key (older records read without them); conversation summary adds the reset time | Asked only of a peer that advertised feature `4`, once a session, after the far message authenticates; answered with a handshake, never a request | Reachable between current clients; an older peer is sent neither type |
| Checkpoint gossip | inner-envelope extension `2` (`tree_size:u64 root:32`); inner message type `7` carrying `GCQ` `1` / `GCA` `1` ([`checkpoint-gossip-v1.md`](checkpoint-gossip-v1.md)) | local record `checkpoint-gossip/v1` (`CGS` `1`); trust alarm kind `3` (`contact_fork`) in `trust-alarms/v1` | Extension 2 is optional and ignored by builds that predate it; type 7 goes only to a device that sent extension 2, `GCQ` or an asking `GCA`, so older builds never receive it (they would reject it unshown). Group messages carry no hint until the next group wire version | Reachable between current clients; new native builds needed for `mesh_messenger_gossip_check` |
| Group messaging | commits `1`/`2` (frame `GCM` `1`, or `2` when the commit moves the group to the committer's witness set), welcomes `GWL` `1` (version 1 policy) and `2` (policy names a witness set and its k), messages `1`/`2`/`3`/`4`/`5`/`6`, recipient transport `SGP` `1`, suite `0x0003` | group snapshots `1`/`2` in frame `GST` `1`, or `2` when the policy names a witness set; storage purposes `12`, `16` and `17` | New groups use state/commit `2` and recipient-wrapped messages `4`; legacy reads retain their original semantics; authenticated epoch transition required for upgrade; reject downgrade. A version 1 welcome reads as 2 of 2 under the version 1 set; a welcome or commit naming a set the build does not know waits (`group_witness_set_unknown`, update Morse) | Reachable custom protocol; internal verification required; not RFC 9420 wire-compatible |
| Disappearing and view-once messages, safety codes | group message `5` whose plaintext is `GOP` `1` (flags: `1` view-once, `2` timer change) ([mls-groups-v1.md](mls-groups-v1.md#disappearing-and-view-once-messages)); inner message type `8` (view-once, a presented message); safety code `morse-verify:1:` ([safety-number-qr-v1.md](safety-number-qr-v1.md)); policy action `6` (unverify after a mismatched code) | group history records of 11 fields (expiry, kind; 7/8/9 still read), `group-timer/v1/<group>`, `expired-objects/v1`; direct and group history summaries gain the kind (and groups the expiry); journal key `settings/app-lock` | A group message is version 5 only when it is view-once, a timer change, or sent under a timer; otherwise version 4. Builds older than this one drop version 5 and inner type 8 unread (acknowledged, never shown), so they never show or keep a timed group message or a view-once message; the sender is not told. The later timer stamp wins, then the longer timer | Reachable between current clients; new native builds needed for the nine new exports and app lock (`MorseLock`) |
| Deniable group messages | group message `6` (version 5 signed with a per-sender, per-epoch Ed25519 key); inner message type `9` carrying `GSA` `1` (76 bytes); session feature bit `8` in inner-envelope extension `3` ([mls-groups-v1.md](mls-groups-v1.md#deniable-sender-authentication)) | `group-signing/v1/<group>` (this device's epoch, mode and sealed key, purpose `7`); `group-signers/v1/<group>` (keys other devices announced); both forgotten with the group; `group_inspect` gains an eighth field (0/1/2), which the app reads with or without it | A device signs an epoch with version `6` only when, at its first message there, every other member device has a steady session with it whose peer advertised bit `8`, so builds before it never receive type 9 or version 6; otherwise it signs version `4`/`5` as before and reports it. The first message fixes the epoch's mode; a later capability starts a new epoch. A receiver opens version `6` only under the key the sender leaf's device announced for that epoch (none yet: `group_sender_key_pending`, retried) and refuses versions `1`–`5` from a device that announced one for the epoch (`group_downgrade_rejected`). Commits and welcomes stay long-term signed | Reachable between current clients; new native builds needed, no new exports |
| Attachments | attachment wire `1` and `2` (`AMF` version `2` pads the object to one of 53 size buckets and fills the manifest to 446 bytes; `EAM` and `ACH` frames stay version `1`); files over 16 MiB (to 512 MiB, 8,192 chunks) grant with `CRD ‖ OGR`, action `4` ([attachment-wire-v1.md](attachment-wire-v1.md#large-files-over-16-mib)) | none; hosts persist only sealed manifests and chunks; object store tables widened in place to 8,193 parts and 537,199,106 bytes | Senders create version 2; readers accept 1 and 2, so version 1 attachments stay readable until they expire. The core's prepare output gains the chunk count, which the host uploads, padding-only chunks included; its prepare request takes an optional sixth vector of credit tokens. A large file is a version 2 manifest of more than 256 chunks: builds from before large files refuse it (`invalid_attachment_manifest`) and show the message without the file, and an object store from before them refuses its grant (`400`). Grants of up to 257 parts are unchanged and never need credits. Reject changed manifests, wrong chunk indices, non-canonical sizes, a chunk count the bucket doesn't imply, nonzero padding, oversized input, and trailing bytes | Development only; streaming mobile and object-store integration required; large files need the credits client and a Mesh release with `Crypto.BlindRsa` on the core |
| Encrypted backups | backup wire `2` ([backup-wire-v1.md](backup-wire-v1.md#version-2-backups-in-the-object-store)): recovery profile `1` (Argon2id v1.3), an attachment wire version 2 object (`AMF` `2`, MIME `application/vnd.morse.backup`) in one of four slots per UTC day, snapshot `BKS` `1` (six sections; the last carries the account key sealed under a code-derived storage key, purpose `6`); frames `EBM`/`BCH` version `1` never stored | device records `backup/v1`, `backup-outgoing/v1[/i]`, `backup-restore/v1[/i]`; the derived key under storage purpose `5`; the object store unchanged | Snapshots are read only by a device of the same account; a restore adds to what the device holds and never replaces it. Parameters are fixed per version; reject a changed manifest, a wrong key, wrong chunk indices, sizes or padding, a snapshot that does not parse, and trailing bytes. Builds before backups ignore the objects, which look like attachments; backups need no service change | Reachable on mobile and desktop; new native builds needed for the thirteen `mesh_messenger_backup_*` exports; the account key is sealed with `StorageKey.from_secret`, which needs a Mesh release that has it (until then the development compiler) |
| Push provider tokens | sealed-token and broker-wake wire `1` | directory stores only broker-sealed ciphertext | Only the configured broker key can open a provider token; reject unsupported providers, malformed tokens, tampering, oversized input, and trailing bytes | Development only; production provider adapter and mobile registration required |
| Directory and delivery | delivery wire `1`; request stamps and envelope proofs at per-endpoint steps from the configured difficulty (register `d`, lookup and prekey claim `d - 2`, envelope `d - 4`) | migrations `001`–`022` (`018`: credit spent set, holds, issuer keys, credit mode; `022`: mailbox policies, paid storage, spend totals, a registration-time index; `021`: consumed one-time prekeys deleted a day after their claim with each device's `pruned_prekey_id`, envelope, push-wake and rate-window times kept to the minute) | Clients and services reject unsupported versions and trailing data. No step is above the configured difficulty, so a directory and edge with the steps accept every stamp an older build mints: deploy them first. Migration `021` must run before the directory that reads `pruned_prekey_id`; the older directory keeps working after it | Development only |
| Key transparency proofs and registry | `KTQ`/`KTA`/`KTS`/`KTI`/`KTC`/`KTE`/`KTW` version `1` (full leaf lists) and `2` (compact RFC 9162 proofs, u64 sizes, `KTP`/`KTL`, kind-1 and kind-2 attestations, C2SP view); C2SP checkpoint note and cosignature lines | migration `017` (witness registry, anchors, C2SP cosignature times); `019` (dense leaf index, both trees' nodes, device-record table, `pruned_at`, no 4,096 check); `020` (entries moved to device records, each verified against its leaf hash) | The directory answers a request in its own version. Version 1 answers exist only while the log holds at most 4,096 entries, then `426`; version 1 stays decodable for one release. Migrations `019`–`020` must run before the directory that reads them, and an older directory cannot read entries after `020` | Development only; phones send only version 2 lookups (`KTQ`/`KTA`) and prove group anchors with `KTS`/`KTC` version 2 on `/v1/transparency/consistency` |
| Oblivious HTTP | RFC 9458 (`message/ohttp-req`, `message/ohttp-res`, `application/ohttp-keys`) with one suite, KEM `0x0020`, KDF `0x0001`, AEAD `0x0003`; known-length Binary HTTP (RFC 9292) inside, padded; relay `POST /v1/ohttp` on the edge, gateway `POST /internal/v1/ohttp` (across deployments `POST /v1/ingress/ohttp`), `GET /v1/ohttp/keys` ([ohttp-v1.md](ohttp-v1.md)) | none on the phone (the response key is held, sealed under purpose `5`, only until its answer is read); the gateway's keys are directory secrets, two at most by `key_id`; the strike register is in memory | A build that pins a gateway (the optional last line of config v2) sends lookups, prekey claims, transparency consistency and leaf proofs, the issuer's keys, and the mailbox fetch and acknowledgement through the relay; every direct route stays for older builds and development builds without a pin. A gateway answers an unknown key id, another suite or a ciphertext that won't open with a bare `422`, a replayed request with an encapsulated `409`. Deploy the directory with the key and the edge with the route before shipping builds that pin the key | Development only; the core, the directory and the CLI need a Mesh release with `Crypto.hpke_seal_export`/`hkdf_aead_seal` (until then the development compiler); new native builds needed for the two `mesh_messenger_oblivious_*` exports |
| Recipient-sealed transport | `RCP` version `1`, outer suite `4`, ratchet message `3` | none; envelopes are opaque to delivery (migration `012`) | New sends always sealed; suite and packet shape must agree; legacy `SIP`/`SGP`/bare packets under outer suites `1`–`3` stay readable until `2026-11-20T00:00:00Z`, 60 days after the first releases that sealed every send (D17). From then each receiver refuses them by its own clock (`legacy_packet_refused`, permanent, so the inbox drops them), with no release needed on the day; a bare initial packet is never read | Development only; update all clients together |
| Direct client transport | `M8P` version `1`, kinds `1` and `2` | inside sealed session/outbox records | CLI and mobile use the same canonical codec and session-bound ratchet AAD; reject wrong kinds, trailing data, identity/session mismatches, and suite mismatches | Development only; Mesh CLI/mobile suite-2 interoperability proof required |
| Security config and phone transparency caches | native frame `messenger/config/v1`, config version `1` (service key, witness A/B keys, delivery key, difficulty, the base of the per-endpoint steps) and `2` (witness set with labels, k, chain anchor, RPC URLs, relays, credit issuer, C2SP origin, minimum suite, and optionally the OHTTP gateway key configuration and relay) | phone view `KTV` `2` (version 1 views with leaf lists are dropped), device-set cache `KTS` `2` (with `set_id`; version `1` is looked up again), witness-set history `KWS` `1`, anchor proof requests `KAQ` `1` | Version 1 reads as witness-a and witness-b, 2 of 2, with the `set_id` of the equivalent version 2 lines; `k` must be the strict majority; a new `set_id` re-verifies cached device sets and keeps the log's continuity; a new service key is refused | Builds write version 2; mobile-core and the CLI read both |
| Credits | token type `0x0002` (RFC 9578, 354 bytes); frames `CRD`, `RDQ`/`RDR`, `HLD`, `CQR`/`CQT` (quotes inside `PWR`), `CIR`/`CIS`, `CIK`, `MBP`, `MRT`/`MRA`, `PKC`, `WRK` version `1`; prekey claim `OTQ` version `2` (answered `PKC`); log leaves `IKY`/`IKR` version `1` ([credits-v1.md](credits-v1.md)) | core: migrations `018` and `022`; issuer: its own database (`services/credit-issuer/migrations`); phones: tokens sealed under the storage key | A body starting `01 "CRD"` carries credits; any other body is read as before, so `PRV`/`PWR` requests are unchanged and credits never become required. `IKY`/`IKR` leaves sit in the same log as device sets; clients that only look up accounts never see them. An `OTQ` version 1 claim is answered as before; only version 2 gets the policy. A `402` from delivery reaches only a sender to a priced public address; a client that does not know postage treats it as an unexplained status and retries later, discarding nothing. Unknown versions, counts outside the packs or 1–64 tokens, and trailing bytes are refused. Clients send `OTQ` version 2 and fall back to version 1 when a directory refuses it. A priced inbox hands its contact address to group members in group packet kind `4` (`GCH` `1`): builds before it refuse the kind as an invalid group packet and drop it unshown. Client records, all sealed: `credits/v1/keys` (`CKS` `1`), `credits/v1/shelves` (`CSH` `1`) and shelves (`CTK` `1`), reservations (`CRI` `1`, `CRS` `1`), purchases (`CPH` `1`), the inbox policy, paid storage, peer prices, and group handovers (`GCL` `1`) | Development only; signing and verifying need a Mesh release with `Crypto.BlindRsa`, and until one ships mobile-core builds only with the development compiler (`Mobile.CreditsIssue`); new native builds needed for the thirteen `mesh_messenger_credits_*` exports |

| Local records | local record format `2` ([storage-wrapping-v1.md](storage-wrapping-v1.md#local-record-format-2)): rows under HMAC-SHA-256 of the label's hash with the database's label key, values masked, no times; SQLite `user_version` `2` | `encrypted_blobs` (`record_hash`, `ciphertext`) and `storage_label_key` (the label key, sealed as purpose `14`); format `1` had rows under the plain SHA-256 of the label and an `updated_at` column, and before that base64 text values | The first open of a format `1` database moves every row in one transaction (base64 values too) and zeroes the pages the old rows leave; an unreadable row or an interruption leaves it in format `1`, unchanged, for the next open. Persisted records and wire messages always carry their existing version. An incompatible field, algorithm, domain label, or canonical encoding requires a new version; it must not silently reinterpret version `1`. Database migrations are forward-only. Rollback is allowed only while the target revision understands every deployed migration, protocol version, suite, snapshot, and native ABI.

CI pins the exact Mesh revision used by Morse. Updating that revision requires protocol, persistence, native-binding, downgrade, and mobile proof reruns before merge.

The earlier private, unversioned mobile direct-message wrapper existed only in development and was never deployed or accepted by a production service. It is retired in favor of canonical `M8P` version `1`; there is intentionally no legacy decoder for that undeployed format.
